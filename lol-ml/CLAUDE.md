# lol-event 승률 예측 모델 (Kotlin ML)

## 목표
- LoL 내전 서비스(lol-event, api.lol.gijun.net)의 경기 데이터로 **게임 시작 전 블루팀 승리 확률**을 예측하는 모델을 Kotlin으로 직접 구현한다.
- 장기 방향: AX 엔지니어 / RAG 구축. 이 모델은 이후 lol-event RAG(Spring AI 또는 Koog + BC-250 llama-server + pgvector)의 tool로 연결되고, 같은 스택을 lab-service(이커머스 포폴)에 재사용한다.
- 목적은 "코틀린으로 AI까지 다 할 줄 아는 사람". 결과물보다 **원리를 직접 구현하며 이해하는 것**이 우선.

## 기술 원칙 (반드시 지킬 것)
- **언어: Kotlin만 사용. 파이썬 코드 작성 금지.** (참고 자료로 파이썬 예제를 읽는 건 OK)
- **1·2단계는 ML 라이브러리 없이 직접 구현** (Smile, DJL 등 사용 금지). 경사하강법, loss, 정규화를 손으로 짠다.
- 빌드: Gradle Kotlin DSL, JDK 21+
- DB 접근: **순수 JDBC** (JPA/ORM 사용 안 함). 의존성은 JDBC 드라이버 정도로 최소화.
- 개발 환경: 1·2단계는 노트북 CPU로 충분. GPU(4060)는 이후 단계에서만.

## 로드맵
1. **1단계 — 로지스틱 회귀 직접 구현** ← 현재 단계
2. **2단계 — Kotlin autograd 엔진** (micrograd 포팅: `Value` 클래스 + `backward()`), 작은 MLP로 플레이어 임베딩(팀케미) 학습
3. ~~텐서 엔진 / Vector API 최적화~~ — AX 목표 대비 ROI 낮아 보류
4. RAG 파이프라인: 학습한 승률 모델을 RAG tool로 연결
5. lab-service에 같은 임베딩/RAG 스택 재사용

## 데이터 원칙
- **LCU로 쌓인 로우 데이터에서 시작한다.** 서비스에 저장된 가공/집계 데이터(현재 Elo, 통산 KDA 등)는 쓰지 않는다.
    - 이유: 미래 정보 누수(leakage), 집계로 인한 정보 손실, 서비스 쪽 가공 로직이 섞임, 과거 시점 값 재현 불가, 피처 실험 불가.
- 원본은 손대지 않고 보존. **정제·피처 생성은 전부 이 프로젝트 코드 안에서, 시간순으로 재현 가능하게.**
- 해당 경기의 KDA·골드·딜량 등은 그 경기의 결과물이므로 **그 경기의 피처로 절대 사용 금지.** 이후 경기 피처를 만드는 재료로만 쓴다.

### 정제 규칙 (스키마 확인 후 확정)
- 다시하기·초반 AFK 경기 제외
- 중복 수집된 경기 제거
- 소환사명/Riot ID 변경으로 쪼개진 플레이어 → 멤버 ID로 매핑

### 도메인 주의사항
- 내전 팀 편성은 자동이 아니라 **한 사람이 세션마다 포지션별 밸런스를 판단해 직접 짠다.** 그래서 실제 승률이 50% 근처로 몰려 있을 가능성이 높다.
    - 정확도보다 log loss / Brier score / 캘리브레이션으로 평가할 것.
    - 0.5 베이스라인을 조금이라도 이기면 "편성자가 놓친 불균형을 잡아낸 것"으로 해석.

## 파이프라인 구조
`추출(JDBC → 로컬 스냅샷 파일)` 과 `학습(파일 → 모델)`을 분리한다.

### 추출
- **읽기 전용 DB 계정** 사용 (운영 DB임).
- `ORDER BY played_at, match_id` 처럼 동점까지 고정된 시간순 정렬은 SQL에서.
- `fetchSize` 설정으로 스트리밍. PostgreSQL이면 `autoCommit = false` 필수.
- 결과는 CSV 또는 JSONL 스냅샷으로 저장 → 학습은 항상 스냅샷 파일로 (재현성, 노트북에서 DB 연결 불필요).

### 1단계 학습 흐름
1. **문제 정의**: 입력 = 블루/레드 각 5명 + 포지션, 출력 = P(블루 승), 손실 = log loss
2. **피처 생성 (point-in-time)**: 경기를 시간순으로 재생하며 플레이어별 상태(Elo, 최근 N경기 KDA, 경기 수)를 유지.
    - 순서 엄수: **현재 상태로 피처 생성 → 그 다음 이번 경기 결과로 상태 갱신**
    - 초기 피처(팀 평균의 블루-레드 차이): Elo 차이, 최근 폼(KDA) 차이, 경험치 `ln(1+games)` 차이
    - Elo는 서비스 값을 쓰지 않고 파이프라인에서 직접 재계산 (초기 1500)
    - 콜드 스타트: 경기 수 적은 플레이어는 기본값 + 경험치 피처로 신뢰도 표현
3. **시간 기준 분할**: 앞 80% 학습 / 최근 20% 테스트. 랜덤 셔플 금지.
4. **표준화**: 학습셋의 평균·표준편차만 사용 (테스트셋 통계 사용 금지)
5. **학습**: 로지스틱 회귀 + L2 정규화, 배치 경사하강법
6. **평가**: 아래 세 개를 비교
    - 상수 0.5 예측 (log loss 0.693, Brier 0.25)
    - Elo 차이만 쓴 모델
    - 전체 피처 모델
    - + 캘리브레이션 표 (예측 확률 구간별 실제 승률)
7. **해석**: 가중치로 "피처 1표준편차가 승률을 몇 %p 움직이는지" 정리 (이후 RAG 설명 근거로 사용)

## 아직 정해지지 않은 것 (작업 시작 시 먼저 확인)
- DB 종류 (PostgreSQL 추정, 미확정)
- LCU 데이터 저장 테이블 구조 (DDL / 엔티티)
- 포지션 컬럼 존재 여부
- 챔피언 정보 사용 여부 = 픽 전 예측만 할지, 픽 후 예측까지 할지

## 작업 방식
- 새 개념(손실 함수 미분, 정규화 등)이 나오면 코드와 함께 짧게 원리를 설명해줄 것.
- 테스트 코드 포함 (특히 피처 생성의 시간순/누수 방지 로직은 테스트로 검증).
