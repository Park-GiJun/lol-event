# lol-event 승률 예측 모델 (Kotlin ML)

## 목표
- LoL 내전 서비스(lol-event, api.lol.gijun.net)의 경기 데이터로 **게임 시작 전 블루팀 승리 확률**을 예측하는 모델을 Kotlin으로 직접 구현한다.
- 장기 방향: AX 엔지니어 / RAG 구축. 이 모델은 이후 lol-event RAG(Spring AI 또는 Koog + BC-250 llama-server + pgvector)의 tool로 연결되고, 같은 스택을 lab-service(이커머스 포폴)에 재사용한다.
- 목적은 "코틀린으로 AI까지 다 할 줄 아는 사람". 결과물보다 **원리를 직접 구현하며 이해하는 것**이 우선.

## 기술 원칙 (반드시 지킬 것)
- **언어: Kotlin만 사용. 파이썬 코드 작성 금지.** (참고 자료로 파이썬 예제를 읽는 건 OK)
- **1·2단계는 ML 라이브러리 없이 직접 구현** (Smile, DJL 등 사용 금지). 경사하강법, loss, 정규화를 손으로 짠다.
- 빌드: Gradle Kotlin DSL, JDK 21+
- DB 접근: **순수 JDBC** (JPA/ORM 사용 안 함). 의존성은 JDBC 드라이버 정도로 최소화.
- 개발 환경: 1·2단계는 노트북 CPU로 충분. GPU(4060)는 이후 단계에서만.

## 로드맵
1. **1단계 — 로지스틱 회귀 직접 구현** (끝)
2. **2단계 — Kotlin autograd 엔진** (micrograd 포팅: `Value` 클래스 + `backward()`), 작은 MLP로 플레이어 임베딩(팀케미) 학습 (끝 — `autograd/Value.kt` · `Mlp.kt` · `model/TeamEmbeddingModel.kt`)
3. ~~텐서 엔진 / Vector API 최적화~~ — AX 목표 대비 ROI 낮아 보류
4. RAG 파이프라인: 학습한 승률 모델을 RAG tool로 연결 (끝 — 아래 "서비스로 넘기기")
5. lab-service에 같은 임베딩/RAG 스택 재사용

## 데이터 원칙
- **LCU로 쌓인 로우 데이터에서 시작한다.** 서비스에 저장된 가공/집계 데이터(현재 Elo, 통산 KDA 등)는 쓰지 않는다.
    - 이유: 미래 정보 누수(leakage), 집계로 인한 정보 손실, 서비스 쪽 가공 로직이 섞임, 과거 시점 값 재현 불가, 피처 실험 불가.
- 원본은 손대지 않고 보존. **정제·피처 생성은 전부 이 프로젝트 코드 안에서, 시간순으로 재현 가능하게.**
- 해당 경기의 KDA·골드·딜량 등은 그 경기의 결과물이므로 **그 경기의 피처로 절대 사용 금지.** 이후 경기 피처를 만드는 재료로만 쓴다.
- **예외 — 랭크 게임 티어(`data/ranks.tsv`).** 내전 기록만으로는 정보가 모자라 내전 밖에서 가져온다. Riot API 는 과거 어느 날의 티어를 주지 않아서 **조회한 날의 티어를 그 전 경기에도 쓴다. 미래 정보인 줄 알고 쓴다.**
    - 새는 것은 랭크 게임의 결과이지 내전 승패가 아니다. 그래도 티어가 들어간 모델의 점수는 그만큼 낙관적이다.
    - `ranks` 를 주기적으로 다시 받아 날짜별로 남겨 두면 그 뒤 경기는 누수 없이 맞출 수 있다(아직 안 한다).

### 정제 규칙 (스키마 확인 후 확정)
- 다시하기·초반 AFK 경기 제외
- 중복 수집된 경기 제거
- 소환사명/Riot ID 변경으로 쪼개진 플레이어 → 멤버 ID로 매핑

### 도메인 주의사항
- 내전 팀 편성은 자동이 아니라 **한 사람이 세션마다 포지션별 밸런스를 판단해 직접 짠다.** 그래서 실제 승률이 50% 근처로 몰려 있을 가능성이 높다.
    - 정확도보다 log loss / Brier score / 캘리브레이션으로 평가할 것.
    - 0.5 베이스라인을 조금이라도 이기면 "편성자가 놓친 불균형을 잡아낸 것"으로 해석.

## 파이프라인 구조
`추출(JDBC → 로컬 스냅샷 파일)` 과 `학습(파일 → 모델)`을 분리한다.

### 추출
- **읽기 전용 DB 계정** 사용 (운영 DB임).
- `ORDER BY played_at, match_id` 처럼 동점까지 고정된 시간순 정렬은 SQL에서.
- `fetchSize` 설정으로 스트리밍. PostgreSQL이면 `autoCommit = false` 필수.
- 결과는 CSV 또는 JSONL 스냅샷으로 저장 → 학습은 항상 스냅샷 파일로 (재현성, 노트북에서 DB 연결 불필요).
- `extract` 는 경기(`data/matches.tsv`), `ranks` 는 티어(`data/ranks.tsv`)를 받는다. `ranks` 는 DB 의 Riot ID 로 Riot API 계정을 찾는다 — DB 의 puuid 는 롤 클라이언트 것이라 Riot API 의 puuid 와 다르다. 환경변수 `RIOT_API_KEY` 가 더 필요하다.

### 1단계 학습 흐름
1. **문제 정의**: 입력 = 블루/레드 각 5명 + 포지션, 출력 = P(블루 승), 손실 = log loss
2. **피처 생성 (point-in-time)**: 경기를 시간순으로 재생하며 플레이어별 상태(Elo, 최근 N경기 KDA, 경기 수)를 유지.
    - 순서 엄수: **현재 상태로 피처 생성 → 그 다음 이번 경기 결과로 상태 갱신**
    - 초기 피처(팀 평균의 블루-레드 차이): Elo 차이, 최근 폼(KDA) 차이, 경험치 `ln(1+games)` 차이
    - 자리 피처: 이번에 앉은 자리에서 한 경기 비율(`seatShare`) 차이, 그 자리에서 Elo 기대보다 더 이긴 정도(`seatEdge`, 표본만큼 0 쪽으로 수축) 차이
    - Elo는 서비스 값을 쓰지 않고 파이프라인에서 직접 재계산 (초기 1500)
    - 콜드 스타트: 경기 수 적은 플레이어는 기본값 + 경험치 피처로 신뢰도 표현
3. **시간 기준 평가 (walk-forward)**: 경기 i 는 그 앞 경기로만 학습해 맞춘다. 처음 60경기 뒤의 모든 경기가 평가 대상. 랜덤 셔플 금지.
    - 앞 80% / 뒤 20% 로 한 번 자르면 평가가 32경기뿐이라 숫자가 흔들렸다.
4. **표준화**: 매 걸음 학습 표본의 평균·표준편차만 사용 (맞출 경기의 통계 사용 금지)
5. **학습**: 로지스틱 회귀 + L2 정규화, 배치 경사하강법
6. **평가**: 아래 세 개를 비교
    - 상수 0.5 예측 (log loss 0.693, Brier 0.25)
    - Elo 차이만 쓴 모델
    - 전체 피처 모델
    - + 캘리브레이션 표 (예측 확률 구간별 실제 승률)
7. **해석**: 가중치로 "피처 1표준편차가 승률을 몇 %p 움직이는지" 정리 (이후 RAG 설명 근거로 사용)

## 2단계에서 알게 된 것 (2026-10)
- autograd 로 학습한 로지스틱 회귀는 손으로 유도한 것과 가중치가 소수점 9자리까지 같다.
- 임베딩 모델(배울 숫자 약 320개, 경기 160개)은 기본값(가운데 4, 150 epoch)에서 본 경기 0.6195 / 안 본 경기 0.7429 로 과적합이 가장 심하다.
    - 72개 조합을 훑었다. 가운데 2 · 50 epoch 이 0.6548 / 0.6907 로 가장 낫지만 0.5 와 구분되지 않는다. 더 누르면(l2 0.1 이상) 정확히 0.5 만 낸다. 이 데이터에서는 쓰지 않는다.

## 내전 밖 정보에서 알게 된 것 (2026-10, 평가 100경기)
- 77명 전원을 Riot API 에서 찾았다. 솔로랭크 71명, 자유랭크만 5명, 언랭 1명. 브론즈부터 마스터까지 퍼져 있다.
- **팀 평균 티어 차이 하나가 내전 기록으로 만든 어떤 피처보다 낫다**: 0.6542 (자리 라인 승률 0.6706).
- 편성자가 티어를 맞춰 놓았을 것이라는 짐작은 틀렸다. 팀 평균 티어는 경기마다 반 티어쯤(1 표준편차 0.53) 벌어진다.
- 자리 라인 승률 + 티어 두 개짜리가 0.6470 으로 가장 낮다. 본 경기와의 차이도 +0.0103 뿐이다.
- 라인 Elo 를 1500 대신 티어에서 출발시키면(한 티어 = 100점, 결과를 보기 전에 정했다) 공식 그대로 0.6663 이다(라인 Elo 공식 0.6828).
- 기존 모델과 경기마다 맞대어도 다섯 쌍 모두 티어 쪽이 낫지만(−0.016 ~ −0.033) 구간은 전부 0 을 걸친다. 가장 가까운 것이 티어 라인 Elo 공식 vs 라인 Elo 공식: −0.0165 (−0.0349 ~ +0.0018).
- 여전히 어느 것도 95% 구간이 0 을 벗어나지 못했다. 그리고 티어가 들어간 숫자는 위의 누수만큼 낙관적이다.
- RAG tool 로 연결한 것은 "자리 라인 승률 + 티어" 다.

## 서비스로 넘기기
**학습은 여기서 하고 서비스(`backend/main-service`)는 숫자만 받아 계산한다.**

- `./gradlew run --args="export"` 가 전체 경기로 학습한 계수를 `backend/main-service/src/main/resources/ml/win-model.json` 에 쓴다. 그 파일을 커밋하고 서비스를 배포하면 반영된다.
    - 계수는 가중치 ÷ 표준편차다(bias 도 평균 빼기도 없는 모델이라 표준화를 계수에 접어 넣을 수 있다). 수축 상수(`PlayerState.PRIOR`)와 티어 평균도 같이 싣는다.
- 서비스는 챗봇 tool `predict_match` 로 쓴다. 피처는 서비스가 **같은 공식을 따로 구현해** 지금 기록으로 만든다.
    - `feature/LaneDuels` · `PlayerState.seatLaneWinRate` · `data/MatchCleaner` ↔ 서비스의 `domain/prediction/service/SeatLaneRecords`
    - `feature/TierPrior.score` ↔ 서비스의 `TierScores`
    - **한쪽 공식을 고치면 다른 쪽도 고치고 `export` 를 다시 돌린다.** 어긋나면 계수가 뜻을 잃는다. 같은 스냅샷을 양쪽에 넣어 74명 × 5자리의 자리 라인 승률이 소수 12자리까지 같은 것을 확인했다(2026-10-09).
    - 서비스의 레이팅 이력은 타임라인이 있으면 15분 시점으로 라인 승자를 가린다. 여기는 늘 종료 시점 값이라 서비스도 이력을 쓰지 않고 따로 센다.
- 사람 키는 양쪽 다 puuid 다(비어 있는 옛 기록만 Riot ID). 서비스의 다른 통계는 Riot ID 로 가르지만 `SeatLaneRecords` 만은 여기와 맞춘다 — Riot ID 를 바꾼 사람의 기록이 둘로 갈리지 않는다.
- 서비스의 티어는 물을 때 Riot API 에서 받는 **그날의 값**이라 누수가 없다. 누수는 여기 평가 숫자에만 있다.

## 정해진 것
- DB: PostgreSQL, 데이터베이스 `lol_event` 의 스키마 `lol_event` (`stocksimulator` DB 안의 같은 이름 스키마는 V10 에서 멈춘 옛 것이다).
- 로우 테이블: `matches` ⨝ `match_participants`. 사람 키는 `puuid`, 포지션은 `assigned_position`(비면 UNKNOWN), 팀은 `team_id`(100 = 블루).
- 픽 전 예측만 한다. 챔피언은 피처로 쓰지 않는다.
- 내전 큐는 0 · 3130, 600초 미만은 뺀다 (서비스의 `GameMode.NORMAL` · 레이팅 검증과 같은 기준).

## 1단계에서 알게 된 것 (2026-10, 평가 100경기)
- **팀 승패로 만든 피처(팀 Elo, 승률, 자리 승률, 최근 KDA)에는 정보가 없다.** 전부 기준선 0.693 근처거나 더 나쁘다.
- **라인 맞대결(같은 자리 두 사람 중 누가 더 컸나)에만 정보가 있다.** 자리 라인 승률 0.6706, 서비스의 자리 Elo 공식 0.6804. 둘의 차이는 구분되지 않는다.
- 어느 것도 95% 구간이 0 을 벗어나지 못했다. 주 10~15판이면 3~4개월 뒤에 다시 본다.
- 피처를 다 넣으면 가장 나쁘다(0.737). 피처 하나짜리 모델을 쓴다.
- 피처 모델은 bias 없이 학습한다 — 두 팀을 맞바꾸면 확률이 1 − p 여야 한다.

## 작업 방식
- 새 개념(손실 함수 미분, 정규화 등)이 나오면 코드와 함께 짧게 원리를 설명해줄 것.
- 테스트 코드 포함 (특히 피처 생성의 시간순/누수 방지 로직은 테스트로 검증).
